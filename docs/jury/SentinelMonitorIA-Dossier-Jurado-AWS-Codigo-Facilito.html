Frecuencias y payloads

Heartbeat normal

  • CPU: 25–55%.
  • Memoria: 35–65%.
  • Log: info.
  • Evento: info.
  • Cada 30–60 segundos.

Incidente controlado

  • CPU: 96%.
  • Memoria: 94%.
  • Log: error.
  • Evento: high.
  • Cada 5–10 minutos.

Los valores altos son datos del payload; el productor no genera carga de CPU o memoria real. Cada batch tiene un UUID y tags de trazabilidad:

{"environment":"mvp-demo","synthetic":"true","source":"continuous-demo"}

05 · Criterios AWSCloud y operación
Qué puede revisar el jurado AWS

Arquitectura y gobierno

Arquitectura desplegada

  • S3 Website para frontend.
  • ALB HTTP/80.
  • ECS/Fargate ARM64.
  • RDS PostgreSQL privado.
  • Redis privado con TLS.
  • ECR, Secrets Manager y CloudWatch.

Operación segura

  • EC2 gestionada por SSM.
  • Sin SSH ni puertos nuevos.
  • Usuario no root.
  • Systemd con CPU/memoria limitada.
  • Workers controlados por desired/running count.
  • Acciones externas apagadas.

Controles de alcance

  • RDS y Redis no cambiaron su infraestructura.
  • No se modificaron NAT, rutas o security groups.
  • El notification worker está en 0/0.
  • AI_ENABLE_ACTIONS=false.
  • No se invoca Bedrock ni se usan embeddings.
  • Los datos enviados son sintéticos y etiquetados.

Coste

Se reutiliza una EC2 `t3.micro` ya encendida; el coste marginal del productor es prácticamente cero. No se creó un ECS producer permanente. La fuente consume una fracción limitada de CPU y memoria.

Bloqueos conocidos. CloudFront/HTTPS y autorización Bedrock no forman parte de esta demo. El flujo público usa S3 HTTP y el AI worker responde con reglas determinísticas.

07 · OperaciónDemo y cierre
Runbook breve

Ejecutar y cerrar la evaluación

Recorrido de cinco minutos

  1. Abrir S3 HTTP y hacer `Ctrl+F5`.
  2. Iniciar sesión con la cuenta demo.
  3. Mostrar health del dashboard.
  4. Consultar alertas con el chat.
  5. Mostrar footer Lex V2.
  6. Actualizar alertas y abrir una alerta high.
  7. Mostrar `analysis_id` y evidencia CPU.
  8. Mostrar notification worker 0/0 y cola notifications 0.

Si el chat responde 401

localStorage.removeItem("sentinelmonitoria.session");
location.reload();

Después iniciar sesión de nuevo. El API key del productor no sirve como access JWT.

Si no aparece una alerta

El heartbeat normal no genera alertas. Esperar 5–10 minutos o ejecutar previamente el smoke incident desde SSM; después de recibir HTTP 202, actualizar el dashboard.

Cierre posterior

  1. Detener el servicio por SSM: systemctl disable --now sentinel-mvp-demo-producer.service.
  2. Revocar la API key del productor sintético.
  3. Desactivar o cambiar el usuario demo.
  4. Retirar secretos de los documentos si el repositorio se publica.
  5. Revisar ECS, RDS, Redis, ALB, S3, CloudWatch y EC2 para controlar costes.
